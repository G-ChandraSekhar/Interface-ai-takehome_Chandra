# Design Report

## 1. Architecture

The system is a single Python process organized as independent, model-agnostic modules, exposed through three interfaces: a CLI (`src/cli.py`) with `discover`, `distill`, `replay`, and `stability` subcommands; a capability API (`src/capability_api/`, FastAPI); and an operator console for human escalation (`src/escalation/console.py`). All three sit on top of the same underlying modules — there is no duplicated logic between "the CLI path" and "the API path."

Discovery (`src/discovery/`) is the only place an LLM appears. `digest.py` turns the live page into a semantic observation — a numbered list of interactive elements by role/accessible-name, plus the page's visible text — rather than handing the model raw HTML; the model picks a *reference* (`e3`), never authors a selector. `tools.py` is the only way the model can affect the world, and every action-taking tool passes through the guardrails policy engine before touching the page. `loop.py` runs observe → decide → policy-check → act until the goal's declared outputs are all marked and `finish` is called.

Replay (`src/replay/engine.py`) is a completely separate, LLM-free execution path that consumes the same artifact format discovery produces. It shares no LLM or decision-making code with discovery — it does reach back for two narrow, deliberate utilities (`EvidenceWriter` from `src/discovery/evidence.py`, and `label_proximity_locator` from `src/discovery/digest.py`, imported so capture and replay resolve that strategy identically), never for anything model-facing. This split is deliberate and is the system's central thesis: the model discovers a capability once; the artifact is what gets invoked from then on, cheaply and deterministically.

Key decisions and trade-offs:
- **Python 3.9-compatible codebase.** Development happened against a Python 3.9 machine, so `from __future__ import annotations` and `typing.Optional` (rather than `X | None`) are used throughout — Pydantic evaluates type annotations at runtime, so the newer union syntax fails there even with the `__future__` import, while plain dataclasses tolerate it.
- **A self-built mock target** (Flask, server-rendered, deliberately legacy: nested tables, no test IDs, sparse semantics) instead of a public site. This was the only way to get deterministic, on-demand fault injection (`mock_app/chaos.py`) for the error paths the brief requires evidence of, without terms-of-service or PII risk.
- **Login is an authenticated precondition**, not part of the LLM-driven trace — a real deployment would inject session material the same way; asking the model to type credentials on every discovery run would be noise, not signal.

## 2. Artifact schema

An artifact (`src/artifact/schema.py`, strict Pydantic, `extra="forbid"`) is a capability contract, not a transcript. It records: scope (`target`: tenant, origin, route prefix); typed `input_params`/`output_schema`; an ordered list of `steps`, each with a **ranked locator ladder** rather than a single selector, plus the click's own destination URL for policy classification; a `checkpoint` (a URL pattern, cheap to verify); and `output_extraction` rules — a label to search for on whatever page replay ends on, not a frozen value.

The ladder is ordered by how tightly each strategy is coupled to things that change, and each candidate carries that as an explicit confidence score: `role_name` (0.9) → `label_proximity` (0.85) → `css_name_attr` (0.75) → `css_id` (0.7) → `text` (0.55) → `positional` (0.2, a recorded admission that nothing stable was found). Only strategies that actually resolve uniquely at capture time are recorded, so a ladder's length varies by control — a link with an accessible name gets several candidates, a bare input in a legacy table gets fewer.

`label_proximity` exists specifically for that last case and is worth calling out, because it was added after inspecting a real distilled artifact and finding a single-candidate "ladder." Legacy table forms frequently give an input no accessible name at all — no `<label for>`, no `aria-label`, no placeholder — so Playwright's accessible-name algorithm correctly yields nothing and `role_name` produces no candidate. `label_proximity` locates the control by the visible label text in the preceding table cell, which is both what a human operator actually reads and what tends to stay constant across tenants running the same vendor product. It ranks *above* the CSS `name=` attribute deliberately: the attribute is an implementation detail that varies per tenant, which is not hypothetical here — Tenant B renders the same field with `name="acct_holder_no"` instead of `name="member_id"`, and that difference is exactly what the tenant overlay had to patch before this strategy existed.

That output point matters too: an artifact's output is *re-derived* at replay time, not replayed back from discovery. This is what makes `replay --param member_id=8832` correctly return a different member's real balance instead of the one seen during discovery — verified directly (member 8832 → Marcus Ojo/918.20, a member never used in discovery).

`input_ref` vs. `literal_value` on a step distinguishes a caller-supplied value from a fixed part of the flow. The distiller (`src/artifact/distill.py`) builds all of this deterministically from a discovery run's `log.jsonl` — a value becomes `input_ref` only if it exactly matches one of the invocation parameters, never guessed by a second LLM pass, so a human reviewer can verify every binding by inspection.

## 3. Determinism & error handling

Replay resolves each step's locator ladder against whatever page it's actually on, in ranked order, and records which tier succeeded — this is the drift signal: if the top-ranked locator stops resolving next month, replay still works and reports it used a fallback. After *every* action (not just at the end), replay checks the current page against pure-text detectors (`src/replay/detectors.py`) for three distinct conditions:

- a **business outcome** (member not found, permission denied) — a legitimate answer, short-circuits cleanly to `status: business_outcome` with a code, never treated as a crash;
- a **recoverable condition** (a session-expired interstitial) — replay clicks through it, bounded by `max_recovery_attempts_per_step`, and continues;
- a **hard failure** (an application error page, an exhausted locator ladder, a missing required parameter, an unmet checkpoint) — reported with a `FailureClass`, the step, what was expected, and what was observed.

The checkpoint is a URL pattern, which on its own would be weak — a URL can be correct while the page behind it is broken. It isn't relied on alone: the detectors above run after *every* action, so a page that is structurally wrong is caught by the error/outcome classification well before the checkpoint is reached. The division is deliberate — the checkpoint answers "did we arrive where this capability claims to end," the detectors answer "is this page healthy," and those are separate questions. When a locator ladder is exhausted, replay reports each candidate's rejection reason individually (`not_unique (matched 3)`, `not_visible`, `no_match`) rather than a bare "nothing resolved," so a failure can be diagnosed from the evidence bundle without reproducing the run.

This produces a genuine three-way `ReplayResult` (`success` / `business_outcome` / `failure`), validated against five real scenarios with zero LLM involvement: same-member success, different-member success (the parameterization proof above), `MEMBER_NOT_FOUND`, `PERMISSION_DENIED`, and a chaos-injected `session_timeout` that recovers and still succeeds (`recovery_applied: True` in the telemetry).

Three real bugs surfaced and were fixed while building this, each worth naming because each was a genuine design lesson, not a typo:
1. The mock app's templates used relative form actions/links, which resolve incorrectly against a URL with no trailing slash (`/desk` + relative `search` → `/search`, silently dropping the tenant prefix). Fixed across all templates.
2. The guardrails policy check for a click was checking the *current* page's risk tier instead of the *destination's* — meaning a click into a mutating route from a safe page would have wrongly been allowed. Fixed by capturing each click's actual destination at discovery/distill time and checking policy against that.
3. The distiller was attributing a click step's destination to the *next* step instead of its own (a misunderstanding of when `page_url` gets logged relative to the action) — harmless only by coincidence in the one artifact built so far, since both steps happened to carry the same policy risk tier. Fixed and regression-tested.

## 4. Heterogeneity & multi-tenant

The seam between "how the surface is perceived/acted on" and "the recorded flow" is `digest.py`/`tools.py` on the discovery side and `locator_resolver.py` on the replay side — both are Playwright-specific today, but neither the artifact schema nor the replay engine's decision logic (business-outcome detection, checkpoint matching, extraction) has any browser dependency. Extending to a legacy web app needs no design change (the mock app already exercises table layouts, no test IDs, sparse semantics). Extending to a desktop app would mean a new implementation of the same locator-ladder contract using OS accessibility APIs (UI Automation on Windows, AX on macOS) in place of Playwright role/CSS/text — a real but bounded addition; not built here, by design (see Cuts).

Multi-tenant reuse is demonstrated for real, not just designed. `src/artifact/overlay.py` is a small, reviewable JSON patch mechanism — `artifacts/overrides/lookup_member_savings_balance@b.json` adapts the Tenant A artifact to Tenant B. Because both tenants render their pages from the same shared templates, only three things actually differ: origin/route prefix, the checkpoint's route shape, and the one form field whose underlying HTML `name` attribute differs (`member_id` vs. `acct_holder_no`). Every other step — including both output-extraction rules — needs zero changes, because both tenants render the identical label text ("Member Name", "Regular Savings"). Live-verified: the same artifact returns Dana Whitfield/2,410.55 unmodified against Tenant A, and Priya Nandakumar/5,002.00 against Tenant B with the overlay applied, through Tenant B's own branded UI and route structure. Locator-tier telemetry is the natural drift signal at scale: if a tenant's markup diverges further, replay degrades to a lower ladder tier and reports it, rather than failing silently — a natural trigger for "this tenant needs its own overlay reviewed."

## 5. Escalation & handoff

`src/escalation/` implements a real pause → human control → resume cycle, not a TODO. A `ControlLease` state machine (`AGENT_RUNNING → PAUSED → HUMAN_CONTROL → RESUMING → AGENT_RUNNING`) decides who may act on the page; an `Intervention` record carries the context an operator needs (run, goal/capability, step, reason, page URL, screenshot); a minimal local FastAPI console (loopback-only, no auth — a documented scope choice, see Safety) exposes **Take control** / **Hand back**. The console is deliberately a *signaling plane, not a remote desktop*: the human drives the actual, visible, headed browser window directly with their own mouse and keyboard; the console never proxies a click.

A real concurrency constraint shaped this design: Playwright's sync API is not thread-safe, but the console runs in a background thread while the paused run blocks on the main thread that owns the page. The console's HTTP handlers therefore only ever flip the lease's state (protected by a lock); all Playwright-touching work — attaching/detaching the navigation recorder — happens inside `HandoffController.wait_for_handback()`, on the same thread that owns the page, by polling the lease and reacting to state transitions itself.

Escalation is wired into both of discovery's stopping conditions: getting stuck (two consecutive turns with no tool call) and exhausting the step/duration budget. In practice, `gpt-4o-mini` proved reluctant to ever go text-only-stuck — it would rather fabricate a plausible-sounding answer than admit it couldn't find what was asked (observed directly during development, though the specific transcript wasn't retained in this repo's evidence). Budget exhaustion was the reliably reproducible trigger, and is arguably the more realistic one in production. Live-verified end to end: a run paused, a real human (not simulated) opened the console, took control, interacted with the actual browser window, handed back, and the run resumed — with a genuine ~40-second gap in the committed evidence timestamps between `intervention_created`, `operator_took_control`, and `operator_handed_back`.

## 6. Safety

A single `PolicyEngine` (`src/guardrails/engine.py`) is the sole point where the allowlist is enforced, called identically by discovery, replay, and the capability API — none of the three trust themselves to self-police. Every action is classified into a risk tier by route pattern: **safe** actions proceed unconditionally; **mutating** actions require either an approved artifact or explicit confirmation; **irreversible** actions can *never* run unattended, under any flag or approval state — the policy engine ignores confirmation flags entirely for that tier, and replay routes such a step to the human-handoff path (a human takes control of the live session, performs or refuses the action themselves, and hands back — replay then verifies the resulting state rather than re-performing the step). Without a handoff route configured, an irreversible step fails closed. This is deliberately structural rather than flag-gated: the guarantee is that an irreversible action in this system cannot execute without a human in the loop at the moment it happens, which is a property of the design rather than of how the tool happened to be invoked. The agent-facing capability API (Phase 5) additionally hardcodes confirmation to `False` and exposes no way for a caller to set it, so a mutating artifact can only run unattended there if it's itself marked `approved`.

Each artifact also carries its own `policy` block (`allowed_origins`, `allowed_actions`) derived at distill time from what the run actually did, enforced by replay **in addition to** the global allowlist — both must permit an action. This means a capability can't quietly widen its reach if the global policy is later loosened for some unrelated capability's sake. A tenant overlay that retargets the origin carries that origin into the artifact's policy (approving the overlay *is* approving that tenant for this capability), still bounded to the base and overlay origins only.

Redaction fully replaces sensitive values with a fixed placeholder rather than partially masking them — a partial mask still leaks the value's length and its first and last characters, which for a short numeric balance or a 4-digit code narrows it considerably.

Redaction is field-name-based for inputs (passwords, supervisor codes — masked before any log write) and a separate, output-value-based rule for financial data (member balance, member name): the value returned to whoever actually invoked the capability stays real, since that's the entire point of the capability existing, but anything persisted to disk — `result.json`, the per-step log — is masked. This was originally incomplete (only credentials were covered) until caught during review and fixed to also cover financial outputs.

A second gap surfaced the same way, during pre-onsite manual testing rather than code review: the click-level block on an irreversible action was correctly enforced (verified by manual inspection during development that no `POST .../subaccount/confirm` reached `mock_app/app.py`'s handler; the mock app has no dedicated request-logging artifact committed to this repo, so that specific check isn't independently reproducible from repo state — the regression test below covers the refusal itself), but without a `--handoff` route configured, nothing stopped the model from calling `finish()` immediately afterward with a fabricated success summary, and the loop reported it as `status: success`. The unsafe action itself was never at risk; the *reported outcome* was lying about it. The fix tracks an unresolved irreversible block explicitly and introduces a distinct `blocked` status that overrides whatever the model's own `finish()` summary claims, so a caller can't mistake a refused action for a completed one. Covered by a regression test (`test_irreversible_block_without_handoff_cannot_be_reported_as_success`) that drives the real mock app through the exact repro.

## 7. Cuts

The clearest limitation used to be that **business-outcome, recovery, and hard-failure detectors were keyed to this app's literal copy, in code** (`src/replay/detectors.py` matching strings like `"No record found for"`) rather than being declared per-artifact — fine for one vendor product, wrong for twenty. This is now built: `Artifact.detectors` (`ArtifactDetectors`/`DetectorPattern` in `src/artifact/schema.py`) lets an artifact declare its own business-outcome, recoverable, and hard-failure markers, checked by `detect_*()` in preference to the hardcoded defaults when present; `distill.py` snapshots the current defaults onto every new artifact so they're explicit and reviewable rather than implicit in code, and an artifact can override them for a different vendor app's copy without anyone touching `detectors.py`. Both current tenants happen to share identical templates (`tenants.py`'s own docstring: "the *same* underlying vendor product"), so there's no second real vendor's copy in this repo to demonstrate against; `tests/test_replay_engine.py::test_artifact_declared_detector_pattern_overrides_hardcoded_default` proves the mechanism honestly with synthetic different-vendor copy instead, paired with a second test proving the *old* code-only path genuinely couldn't classify that same copy — the gap this closes, made concrete.

Two smaller ones in the same spirit. The checkpoint is a URL pattern only (mitigated in practice by detectors running after every action — see §3, but a content assertion would be stronger). And login is handled as an authenticated precondition rather than being part of the LLM-driven trace: a real deployment injects session material the same way, and making a model type credentials on every discovery run would add risk without adding signal, but it does mean auth itself is not a capability this system can discover.

Not built, deliberately, in order of what would come next: a desktop `Surface` implementation (design is stated above; OS accessibility APIs in place of Playwright); full click/keystroke-level human-action recording during handoff (currently navigation-level only — capturing DOM input events would need a script injected into every page the operator might visit); automatic locator repair or an open-ended LLM fallback during replay (the brief's own stretch-goal list, deliberately skipped in favor of the agent-facing capability API); operator-console authentication (bound to loopback, single local demo session, by design); multi-run stability aggregation across many replays over time (per-run locator-tier telemetry and confidence scores exist, and a fallback-rescue event fires when a step resolves below its top tier, and there was no rolling signal across runs -- now closed by the drift detection described below).

Multi-run stability scoring is also now built (`src/replay/stability.py`, `python3 -m src.cli stability --artifact-id X --version 1 --param k=v --runs N [--update-artifact]`): replays the same artifact+params N times sequentially, aggregating success/business-outcome/failure rates and per-step average/worst locator tier -- the earliest available drift signal, since a step's average tier can climb well before success_rate itself shows any decline. Deliberately does NOT gate or auto-set `Artifact.approved`: `--update-artifact` writes the computed report onto the artifact's own `stability` field so it's visible to a reviewer, but approval stays a human's out-of-band decision everywhere else in this codebase (`guardrails/engine.py`, `capability_api/server.py`) -- a computed score is meant to inform that decision, not make it. Two tests (`test_run_stability_aggregates_mixed_outcomes_correctly`, `test_stability_update_artifact_persists_report_without_touching_approved`) prove the aggregation math against a genuinely mixed outcome sequence and confirm `approved` is left untouched.

The remaining half of that gap -- a rolling signal *across* runs rather than within one sitting -- is now built too (`src/telemetry/`, `python3 -m src.cli health`). Stability answers "is this artifact reliable right now"; it cannot see a step that used to resolve at tier 1 and now resolves at tier 3, because it only ever looks at one sitting. Every replay now appends one line of durable history (`telemetry/runs.jsonl`, append-only JSONL, machine-local and gitignored), and `health` compares disjoint baseline and recent windows per artifact, per step. Medians rather than means, because ladder tiers are ordinal positions and the average of tier 1 and tier 5 is not "tier 3" in any meaningful sense -- and because one flaky run should not page anyone, though `worst_recent_tier` still surfaces the outlier so a reader sees "typically tier 1, hit tier 4 once." Rising failure rates *without* tier drift are reported separately, so a reader debugs the application rather than the artifact. Runs produced by `stability` are source-tagged and excluded by default: N runs fired back to back in one minute would swamp a baseline meant to span weeks. Unlike `stability`, `health` exits non-zero on degradation -- the two answer different questions, one a report a human reads before approving, the other a check something runs on a schedule.

Verified live rather than only in tests (`evidence/drift_demo_20260820/`). Ten replays established a baseline with step `s1` resolving at `label_proximity`. Changing one string in `mock_app/tenants.py` -- `member_id_label` from "Member ID" to "Member Number", the kind of harmless copy edit a bank makes without telling anyone -- and running five more produced fifteen consecutive successes, 0% failure rate in both windows, and this:

```
s1: tier 1.0 -> 2.0  (label_proximity -> css_name_attr)  DRIFTING
```

Nothing failed. Nothing had failed. `the_change_that_caused_it.diff` in that evidence directory is the one-line edit that triggered the report. This is the case a single selector cannot surface: the step would have kept passing until the day the `name` attribute changed too, and then failed in production with no warning at all. Ten tests cover the assessment logic against synthetic history, including the cases that matter most -- that steady history is *not* flagged, since a drift detector that cries wolf gets muted, and that thin history reports `insufficient_data` rather than emitting a confident number derived from nothing.

The honest gap this exposes rather than closes: the ladder's confidence priors (0.9, 0.85, 0.75...) are still fixed values, not measurements. The ordering is empirical -- `label_proximity` sits above `css_name_attr` because Tenant B's markup diverges where its visible label does not -- but the numbers themselves were never derived from anything. `telemetry/runs.jsonl` now accumulates exactly the observations that would replace them; wiring that feedback loop is not built.

Next steps, roughly in priority order: a `DesktopSurface` behind the same locator-ladder contract; authenticated console access; click/keystroke-level human-action capture during handoff; recalibrating the locator ladder's confidence priors from accumulated telemetry rather than leaving them as fixed guesses; a second real vendor app to validate the detector-pattern override against genuinely different copy rather than the synthetic proof currently in place.
